**Goal:** Stand up `packages/pg-pr/` as a new Go module with cobra CLI skeleton, package interfaces stubbed, nix package + home-manager module building, ADRs filed, and bd issues created for Phases 1–4. The end state is `nix build .#pg-pr` succeeds, `pg-pr version` prints the version, and no behavioral logic from the source packages has been moved yet.

New Go module path `github.com/phillipgreenii/phillipgreenii-nix-agent-support/packages/pg-pr`. All provider impls, sync engine, bead wrappers are stubs in this phase — bodies return `not implemented` errors. Phase 1+ fills them in.

**Tech Stack:** Go 1.24 + `github.com/spf13/cobra` + nix `buildGoModule` + `help2man` for man pages + standard `golangci-lint` + `gofmt` in pre-commit.

**Source for skeleton:** `packages/my-code-review-support-cli/` — copy structure, not behavior.

```go
package main

import (
	"context"
	"fmt"
	"os"
	"os/signal"
	"syscall"

	"github.com/spf13/cobra"
)

// Version is set at build time via -ldflags.
var Version = "dev"

var rootCmd = &cobra.Command{
	Use:     "pg-pr",
	Short:   "Unified PR-work CLI for agents and humans",
	Version: Version,
}

var versionCmd = &cobra.Command{
	Use:   "version",
	Short: "Print version information",
	Run: func(cmd *cobra.Command, args []string) {
		fmt.Fprintf(cmd.OutOrStdout(), "pg-pr %s\n", Version)
	},
}

func init() {
	rootCmd.AddCommand(versionCmd)
}

func main() {
	ctx, cancel := signal.NotifyContext(context.Background(), syscall.SIGINT, syscall.SIGTERM)
	defer cancel()
	if err := rootCmd.ExecuteContext(ctx); err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
}
```

```go
// the script-out provider protocol. Stubs only in Phase 0; fields are added
// in Phases 1–4 as the surface lands.
package api

// PR is the JSON shape returned by `pg-pr pr show`.
type PR struct {
	Repo     string `json:"repo"`
	Number   int    `json:"number"`
	State    string `json:"state"`
	Branch   string `json:"branch"`
	Base     string `json:"base"`
	Author   string `json:"author"`
	URL      string `json:"url"`
	Draft    bool   `json:"draft"`
	Merged   bool   `json:"merged"`
}

// Comment is the JSON shape for a PR comment.
type Comment struct {
	ID         string `json:"id"`
	Author     string `json:"author"`
	AuthorRole string `json:"author_role"`
	Body       string `json:"body"`
	Path       string `json:"path,omitempty"`
	Line       int    `json:"line,omitempty"`
	ThreadID   string `json:"thread_id,omitempty"`
	Resolved   bool   `json:"resolved"`
}

type Review struct {
	ID       string    `json:"id"`
```

- [ ] **Step 2: Write 0001-pg-pr-go-cli-consolidation.md**

Use the template from `CLAUDE.md` §"ADR Template". Concrete content:

- **Status**: Accepted
- **Date**: 2026-05-20
- **Deciders**: Phillip Green II
- **Context**: PR-agent functionality scattered across six locations using three languages and three orchestration models. Duplicate worktree management, GitHub fetch, PR body generation; two competing bead schemas. Mixed-mode work (human + gascity + claude session) is fragile because each surface talks to GitHub differently.
- **Decision**: Consolidate into a single Go CLI `pg-pr` plus a claude plugin distributed via the existing local-marketplace mechanism. The CLI is the sole interface between agents and external systems (GitHub, jira, CICD) for PR work. LLM callers read/write beads + invoke `pg-pr` only.
- **Consequences (Positive)**: Single source of truth; mixed-mode work supported by shared bead schema; reduced LOC across the six sources.
- **Consequences (Negative)**: Migration takes 5 phases; ZR-specific Captain's Log adapter has to live downstream.
- **Consequences (Neutral)**: New Go module to maintain.
- **Alternatives Considered**: (a) Keep separate tools, paper over with bash glue — rejected because it doesn't solve the cross-actor consistency problem. (b) Build as a Bash CLI — rejected because the existing Go skeleton (`my-code-review-support-cli`) already exists and is more testable.
- **Related Decisions**: See also `docs/superpowers/specs/2026-05-19-pg-pr-design.md`. Supersedes the implicit decisions in `packages/gh-prreview/`, `packages/my-code-review-support/`, and `packages/my-code-review-support-cli/`.

- [ ] **Step 3: Write 0002-pg-pr-extension-via-exec-scripts.md**

- **Status**: Accepted
- **Date**: 2026-05-20
- **Deciders**: Phillip Green II
- **Context**: ZR-specific providers (Captain's Log CICD, ZR-flavored jira) can't live in the org-agnostic `phillipgreenii-nix-agent-support`. We need an extension mechanism that lets `phillipg-nix-ziprecruiter` ship adapters without rebuilding `pg-pr` core.
- **Decision**: Two extension surfaces: (1) provider script-out via `exec:<binary-name>` config entries, where the binary speaks JSON in/out on stdin/stdout per a versioned protocol in `pkg/api/`. (2) kubectl-style command plugins: unknown `pg-pr <verb>` execs `pg-pr-<verb>` from PATH. Extension binaries are themselves Go programs that import `pg-pr`'s `pkg/` library; they do not rebuild `pg-pr` core.
- **Consequences (Positive)**: No cross-repo build coupling. Org-specific code stays in org-specific flakes. Composite providers possible (CICD list).
- **Consequences (Negative)**: Subprocess latency per provider call (acceptable since calls are bounded). Script-out protocol becomes a versioned API the core can't break unilaterally.
- **Alternatives Considered**: (a) Go compile-time plugin registration via the Go `plugin` package — rejected because Go plugins are fragile on Darwin and version-locked. (b) Library-link nix-ziprecruiter's binaries against the same `pg-pr` source — rejected because user wants extensions not to rebuild core.
- **Related Decisions**: `docs/superpowers/specs/2026-05-19-pg-pr-design.md` §"Provider extension protocol".

- [ ] **Step 4: Write 0003-pg-pr-bead-schema.md**

- **Status**: Accepted
- **Date**: 2026-05-20
- **Deciders**: Phillip Green II
- **Context**: Multiple actors (gascity background agents, claude sessions, human CLI use) need to operate on the same PR-related work queue. `bd ready` must just work for any agent with no pg-pr-specific flags. Earlier gc/zr usage introduced typed beads but bd-dep direction created deadlocks when I tried to use deps for cascading closure.
- **Decision**: Four bead types in the schema: `merge-request` (PR tracker, builtin custom type, auto-excluded from `bd ready`); `task` (processing-cycle work unit, surfaces in `bd ready`); custom `feedback` type with `status=hooked` so it's excluded from `bd ready` while remaining closeable; `task` or `bug` (action). Hierarchy via bd's `parent-child` non-blocking dep type. Action→feedback via `discovered-from` soft dep. CLI implements cascade on PR close explicitly. Repo-level errors live in `$XDG_STATE_HOME/pg-pr/repo-state.json`, not in beads.
- **Consequences (Positive)**: Zero pg-pr-specific flags on `bd ready`. Mixed-mode actors share a clean contract. Custom type `feedback` registered additively so existing types stay intact.
- **Consequences (Negative)**: `status=hooked` is a slight semantic stretch (nominally for hook-gated work). Workaround acceptable; behavior validated in Phase 0 scoping work.
- **Alternatives Considered**: (a) Labels for hierarchy + builtin types only — rejected because bd `parent-child` deps already work and produce nicer `bd show` output. (b) `message` type for feedback — rejected because `message` IDs get `wisp-` prefix and may be TTL-compacted, threatening referential integrity for action→feedback links. (c) Custom `action` type — rejected because builtin `task`/`bug` suffice and reduce type proliferation.
- **Related Decisions**: `docs/superpowers/specs/2026-05-19-pg-pr-design.md` §"Bead schema".

- [ ] **Step 5: Write 0004-pg-pr-defer-forgejo-to-v2.md**

- **Status**: Accepted
- **Date**: 2026-05-20
- **Deciders**: Phillip Green II
- **Context**: The design provides for forgejo as an alternate VCS provider, but v1 work targets only GitHub. Building both at once delays the value of consolidation.
- **Decision**: v1 ships GitHub-only. The VCS provider interface (`pkg/provider/vcs/iface.go`) is defined now so a forgejo impl can be added without breaking changes.
- **Consequences (Positive)**: Faster v1 delivery; lower test surface.
- **Consequences (Negative)**: Anyone wanting forgejo today must wait; v1 designs aren't validated by a second impl.
- **Alternatives Considered**: (a) Ship both — rejected because nothing in the user's current workflow requires forgejo. (b) Drop forgejo from the spec entirely — rejected because the interface affordance is cheap and signals future intent.
- **Related Decisions**: `docs/superpowers/specs/2026-05-19-pg-pr-design.md` §"Non-goals (v1)".
