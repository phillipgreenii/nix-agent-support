## Context

PR-agent functionality is currently scattered across six locations using three languages (Python, Go, Bash) and three orchestration models (claude skills, gascity pack, workflow phases). Duplication exists in: worktree management (3x), GitHub fetch (3x), PR body generation (2x), feedback ingestion (2x). Two bead schemas compete. Mixed-mode work (human + gascity + claude session on one PR) is hard because each surface talks to GitHub differently and writes beads differently.

User wants a single Go CLI that owns all non-LLM PR work, exposes a stable contract via beads, and lets any LLM caller (human-run claude session, gascity background agents, manual CLI use) do PR work identically.

## Goals

- Single Go CLI `pg-pr` is the sole interface between agents and GitHub/Forgejo/Jira/CICD for PR work.
- LLM never calls `gh` / `git api` / jira directly for PR workflows. LLM reads/writes beads + invokes `pg-pr`.
- Same flow whether triggered by human at terminal, by `/check-my-pr` skill in claude, or by gascity background poll.
- Mixed-mode operation: gascity handles routine feedback; claude session picks up the rest; human stitches. All actors operate on shared bead graph.
- Provider model is pluggable at runtime via exec-discovered binaries. ZR-specific code (Captain's Log, ZR Jira) lives in `phillipg-nix-ziprecruiter` as separate Go binaries; never rebuilds `pg-pr`.
- One repo, multiple nix module outputs. Org-agnostic core in `phillipgreenii-nix-agent-support`; ZR specifics in `phillipg-nix-ziprecruiter`.

## Non-goals (v1)

- Forgejo VCS support. Interface defined; impl deferred.
- Auto-reply to feedback (sync-driven): deferred to v2. Mechanism TBD.
- Auto-resolve comment threads: deferred to v2.
- Modifying `/Volumes/ziprecruiter/pristine/.claude/` shared org commands. Used as reference only.
- Replacing all current bash workflow commands in pristine (`/git:ship`, `/cicd:watch-pr-checks`, etc.). Their patterns inspire skills in this plugin but pristine stays.

## Architecture

### Two binaries, one library

```text
pg-pr (org-agnostic, built from packages/pg-pr/cmd/pg-pr)
  builtin providers: github VCS, github-actions CICD, jira issues, github-issues
  one binary, statically linked

pg-pr-cicd-captains-log, pg-pr-issues-jira-zr, pg-pr-zr-* (ZR-specific)
  separate Go binaries, built from phillipg-nix-ziprecruiter/modules/pg-pr-zr/cmd/*
  import github.com/phillipgreenii/.../pg-pr/pkg as library
  do not rebuild pg-pr core
  distributed on PATH via the ZR home-manager module
```

### Provider extension protocol

Two extension surfaces:

1. **Provider scripts (exec-style)**. Config references a provider as `exec:<name>`. `pg-pr` spawns the named binary, sends a JSON request on stdin, reads JSON response on stdout. Protocol defined in `pkg/api/`. Builtins implement the same interface in-process.

   Request shape (simplified):

   ```json
   {
     "op": "list_runs",
     "pr": { "repo": "...", "number": 101 },
     "since": "2026-05-19T12:00:00Z"
   }
   ```

   Response shape:

   ```json
   {
     "runs": [{ "id": "...", "status": "failure", "url": "..." }],
     "errors": []
   }
   ```

   Composable: a repo can list multiple CICD providers; `pg-pr` fans out and merges. Used for ZR hybrid (`github-actions` + `exec:pg-pr-cicd-captains-log`).

2. **Command plugins (kubectl-style)**. `pg-pr <unknown>` searches PATH for `pg-pr-<unknown>` and execs it. Stdout passes through. Used for future workflow commands (`pg-pr zr-rollback`, etc.). No builtin commands are exposed this way in v1.

### What pg-pr core ships as library

`pkg/api/` exports:

- JSON schema types for all CLI outputs and the script-out protocol
- `provider.VCS`, `provider.CICD`, `provider.Issues` Go interfaces
- `plugin/scriptout/` helpers — given a `provider.CICD` impl, expose it as a stdin/stdout binary (reduces boilerplate for extension authors)
- `plugin/cmdplugin/` helpers — argv parsing + standard env (`PG_PR_CONFIG`, etc.) for kubectl-style plugins
- `beads/` typed wrappers around `bd` for the four bead types

ZR extension authors write `func main()` that calls a helper:

```go
func main() {
    scriptout.ServeCICD(&captainsLog{...})
}
```

## Bead schema

Uses bd's existing built-in `merge-request` custom type, builtin `task`/`bug`, and registers one new custom type: `feedback`. Repo-level sync errors live in a state file, not in beads.

**bd type assignment**:

| Concept          | bd type                                                | `bd ready` visibility           | Notes                                                                                                                                                        |
| ---------------- | ------------------------------------------------------ | ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| PR tracker       | `merge-request`                                        | auto-excluded by bd             | GitLab/Forgejo's name for the same concept as a GitHub PR. Already registered in this workspace's `types.custom`.                                            |
| Processing cycle | `task` (title prefix `process-feedback:`)              | **visible — primary work unit** | LLM claims via `bd update --claim`.                                                                                                                          |
| Feedback event   | `feedback` (new custom type)                           | excluded via `status=hooked`    | Registered by appending to `types.custom`. CLI creates beads with `status=hooked` so they never surface in `bd ready` independently of the processing cycle. |
| Work item        | `task` (default) or `bug` (for CI failures / breakage) | **visible**                     | LLM picks per situation.                                                                                                                                     |

**Why a new `feedback` custom type** (not `message`): bd's `message` type IDs are prefixed `<workspace>-wisp-…` and the type is part of the TTL-based compaction tier; feedback beads must persist long enough for the action beads created during processing to reference them via `discovered-from`. A dedicated `feedback` type sidesteps the compaction concern.

**Why `status=hooked` for feedback** (not `deferred` / `blocked`): `bd ready` excludes `in_progress`, `blocked`, `deferred`, and `hooked` statuses. `blocked` requires a real blocker dep; `deferred` semantically means "do later"; `hooked` means "ready-state is gated externally" — which fits, because feedback beads are processed only via their parent processing-cycle bead, not claimed directly. CLI sets `status=hooked` at create time; the bead transitions directly to `closed` when the LLM closes it with a reason.

**bd config addition**: `bd config set types.custom "<existing>,feedback"` (preserving previously-registered types). The pg-pr nix module ensures this via an activation step in projects where the bd workspace is owned by the user.

**bd dep types used**: `parent-child` for hierarchy (non-blocking, sets `↑ parent` link visible in `bd show`); `discovered-from` for soft semantic links (action ← feedback it addresses). `blocks` is reserved for genuine work blockers (e.g., action A truly cannot proceed until action B completes).

**`bd ready` invariant**: agents run `bd ready` with no pg-pr-specific flags. Type-based exclusion handles `merge-request`; `status=hooked` handles `feedback`; only `task` and `bug` beads (processing-cycle and action) surface as work units.

### PR-tracker bead (`type=merge-request`)

One per watched PR. CLI lifecycle.

Fields (stored on bead via metadata + description):

- `repo` (e.g., `ziprecruiter/zr-app`)
- `pr_number`
- `state` (`open` | `draft` | `ready` | `closed` | `merged`)
- `branch`, `base`
- `author`
- `url`
- `last_synced_at`, `sync_error`
- `ci_only_attempts` (int, default 0) — incremented when a `process-feedback` cycle closes having addressed only CI failures. Reset to 0 on any new external comment or review.
- `human_block_reason` (string | null) — set when `ci_only_attempts >= threshold`; cleared on reset.

Deps: none incoming. (Process-feedback / action children depend `parent-child` → this bead.)

Lifecycle:

- CLI creates on first detection by sync, or by `pg-pr pr create`.
- CLI updates state from upstream on each sync.
- CLI closes when upstream PR closes or merges; explicitly cascades closure to children (see "Cascading" below).
- CLI maintains `ci_only_attempts` and `human_block_reason` per the CI-loop escalation rules.

### Processing-cycle bead (`type=task`, title prefix `process-feedback:`)

One per active processing cycle for a PR. CLI creates; LLM closes.

Deps:

- `parent-child` → merge-request bead (non-blocking; visible as parent in `bd show`).

Body: rendered instructions for the LLM (see "Process-feedback instructions" below).

Lifecycle:

- Each sync: if there are new/changed feedback events for a PR AND no open processing-cycle bead exists for it, CLI creates one. Otherwise reuses the open one (new feedback nested under same parent).
- LLM claims via `bd update --claim`, processes children, closes when done.

### Feedback bead (`type=feedback`, `status=hooked`)

One per upstream event. CLI creates with `status=hooked` so it's excluded from `bd ready`; LLM closes with reason during processing of the parent processing-cycle bead.

Deps:

- `parent-child` → processing-cycle bead.

Fields (metadata):

- `kind` (`comment-thread` | `ci-failure` | `review-thread` | `review-request` | `jira-link`)
- `external_id` (GitHub thread id or equivalent)
- `fingerprint` (content hash for dedup)
- `author_role` (`self` | `team_member` | `org_member` | `bot`)
- `resolved_upstream` (bool — set by sync when thread resolved / CI green)

Lifecycle:

- CLI creates from sync with `status=hooked`.
- LLM closes during processing of parent (transitions directly from `hooked` → `closed`) with reason:
  - `accept: <plan>; created action <bead-id>` OR
  - `reject: <reason>`
- CLI may auto-close if `resolved_upstream` becomes true on a subsequent sync (reason: `resolved-upstream`).

### Action bead (`type=task` or `type=bug`)

LLM-created. Lives independently after the processing-cycle bead closes.

Deps:

- `parent-child` → merge-request bead (sibling of processing-cycle).
- `discovered-from` → one or more feedback beads (soft, non-blocking link to the feedback that motivated this action).

Fields (metadata):

- `kind` (`fix-ci` | `respond` | `apply-suggestion` | `refactor` | `defer-to-future-pr` | etc.) — guides LLM downstream.

Lifecycle:

- LLM creates during processing of the processing-cycle bead.
- Stays open after processing-cycle closes — that's the actual fix work.
- LLM closes when work is done (commit pushed, decision recorded, deferred to followup PR).

Type choice: `task` for normal work; `bug` for things that are unambiguous breakage (CI failure fixes, regression repairs).

### Repo-level sync errors (NOT a bead)

State file `$XDG_STATE_HOME/pg-pr/repo-state.json`:

```json
{
  "repos": {
    "ziprecruiter/zr-app": {
      "last_synced_at": "2026-05-20T12:00:00Z",
      "last_error": null
    },
    "phillipgreenii/phillipgreenii-nix-agent-support": {
      "last_synced_at": "2026-05-20T11:58:00Z",
      "last_error": { "code": "auth_expired", "message": "gh token expired" }
    }
  }
}
```

Surfaced by:

- `pg-pr auth status` — per-provider, per-repo.
- `pg-pr changes --json` — embeds `errors` block from this file.

Not a bead because the errors are not units of work and would clutter `bd ready` if represented as beads.

### Cascading

bd has no native cascade on close. CLI implements explicit cascade in `internal/sync/cascade.go`:

- When CLI closes a `merge-request` bead (because upstream PR closed/merged):
  - Find all beads with `parent-child` dep to this bead (processing-cycle, action) — close with reason `pr-closed`.
  - For each closed processing-cycle, find its `parent-child` children (feedback) — close with reason `pr-closed`.
- LLM-driven closure of a processing-cycle bead is NOT a cascade trigger; feedback beads should already be closed by the LLM as part of processing. If any remain open at processing-cycle close, sync warns on next run.

## Sync engine

### One-shot flow per repo

1. List PRs of interest (mine + team_members + watch_labels from config).
2. For each PR:
   - Upsert `pr` bead.
   - Fetch comments, reviews, CI runs, jira links since `last_synced_at`.
   - For each new/changed event: upsert `feedback` bead (dedup via fingerprint).
   - For events whose upstream state changed to resolved: mark feedback `resolved_upstream`, close.
   - If any open feedback exists and no open unclaimed `process-feedback` exists: create one.
3. Detect PRs no longer in upstream listing (closed/merged); close `pr` bead and cascade.
4. Per-repo errors are captured in the state file `$XDG_STATE_HOME/pg-pr/repo-state.json` (see "Repo-level sync errors" in the bead schema).

### PR draft lifecycle

- Any PR created via `pg-pr pr create` is created in **draft** mode by default (override flag must be explicit).
- On each sync, if a `pr` bead is in `draft` state and all CICD runs for that PR are green (CI-only — user approval is not part of this gate), CLI calls `pg-pr pr ready <id>` (idempotent) to move the upstream PR out of draft.
- Sync never moves a PR back to draft. Draft→ready is one-way (the user or PR author can revert manually if needed).
- Failing CICD never demotes a ready PR back to draft.

### CI-loop escalation

To prevent agents from churning on a flaky or genuinely-broken CI failure forever:

- Each time a `process-feedback` cycle closes for a PR, CLI inspects the closed-with-accept feedback children:
  - If **all** accepted feedback was of kind `ci-failure` (no comment/review/review-request was addressed), CLI increments `pr.ci_only_attempts`.
  - If **any** non-CI feedback was accepted, CLI resets `pr.ci_only_attempts = 0`.
- On any new external comment or review fetched in a subsequent sync, CLI resets `pr.ci_only_attempts = 0` and clears `human_block_reason`.
- When `ci_only_attempts >= config.ci_only_attempts_threshold` (default `3`):
  - CLI sets `pr.human_block_reason = "ci-only-loop: <N> consecutive cycles without external feedback resolved; CI still failing"`.
  - CLI calls `bd human <pr-bead-id>` with the same message.
  - CLI stops creating new `process-feedback` beads for this PR until the block is cleared.
- Clearing the block: new external comment/review fetched on next sync clears `human_block_reason`, dismisses the `bd human` flag, and resumes `process-feedback` creation.

### Daemon mode

`pg-pr sync --daemon --interval 10m`:

- Single-instance enforced via flock at `$XDG_RUNTIME_DIR/pg-pr/daemon.lock`.
- Loop: `sync()` → sleep `interval` → repeat.
- SIGHUP reloads config without restart.
- SIGTERM finishes current iteration and exits cleanly.
- Logs to stderr; `--log-json` switches to structured.
- Nix module installs systemd user unit on Linux, launchd agent on macOS.

### Change feed

`pg-pr changes --since <RFC3339>`:

- Source: bd query for beads where `updated_at > ts`.
- Errors enriched from `sync_error` field on `merge-request` beads and from `$XDG_STATE_HOME/pg-pr/repo-state.json` for repo-level errors.
- Output JSON with sections: `created`, `updated`, `closed`, `errors`.

Used by gascity to learn what happened since last poll. No separate audit log.

## Author precedence

`feedback.author_role` set at sync time:

| Role          | How determined                                                                                                                                 |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `self`        | Comment author equals configured `self_login`.                                                                                                 |
| `team_member` | Author in `repos[].team_members` config list.                                                                                                  |
| `org_member`  | Author has membership in configured org (resolved via GH org membership API; cached at `$XDG_CACHE_HOME/pg-pr/org-members.json` with 24h TTL). |
| `bot`         | Author matches builtin bot list (`dependabot[bot]`, `github-actions[bot]`, `copilot[bot]`, …) or has `type: Bot` in GH API.                    |

Precedence (high → low): `self > team_member > org_member > bot`. Encoded in `process-feedback` body so LLM applies it consistently:

> Self comments are directions. If Phillip says do X, do X. Self questions or non-actionable musings: include in context, may decide not to act. team_member > org_member > bot reflects descending weight. Bot feedback is lowest priority unless it indicates a hard failure (e.g., CI red).

## Process-feedback bead instructions

Body template (rendered by CLI when creating bead):

```text
You are processing review feedback for PR <repo>#<number>.

Each child `feedback` bead represents one upstream event (comment thread, CI failure,
review thread, review request, or jira link). For each:

1. Read the feedback and decide:
   - ACCEPT and implement now → create an `action` bead (sibling of this bead) with
     a clear scope. Label the action `addresses-feedback: <feedback-id>`.
   - ACCEPT and defer to future PR → create an `action` bead of kind `defer-to-future-pr`
     describing what's being deferred and why.
   - REJECT → close the feedback with reason `reject: <explanation>`.
2. Close the feedback bead with reason `accept: <plan>; action <id>` OR `reject: <why>`.
3. If you are unsure about any feedback, leave it OPEN and mark this process-feedback
   bead via `bd human` with a clear question for Phillip.

Author precedence (high → low): self > team_member > org_member > bot.
- self = Phillip's own comments. Instructions = do. Questions = context only.
- bot feedback is lowest unless it's a hard failure (CI red, security finding).

NEVER call `pg-pr pr merge` or `pg-pr pr automerge on|off`. These verbs exist for
human use only. If the work appears complete and ready to merge, leave the PR
in its current state and surface that conclusion via the closing reason or by
marking the process-feedback bead `bd human`.

Close this process-feedback bead only after every feedback child is closed
OR you have marked this bead `bd human`.
```

Instruction text is templated; CLI substitutes PR identifier and resolved configuration.

```yaml
  - path: /Users/phillipg/phillipg_mbp/phillipgreenii-nix-agent-support
    remote: phillipgreenii/phillipgreenii-nix-agent-support
    vcs: github
    cicd: github-actions
    issues: github-issues
    org: phillipgreenii

daemon:
  interval: 10m

ci_only_attempts_threshold: 3 # default; per-repo override allowed
```

Resolution rules:

- `vcs`, `cicd`, `issues` values are provider names. Builtin names: `github`, `github-actions`, `jira`, `github-issues`. External providers: `exec:<binary-name>` (resolved against PATH).
- `cicd` may be a single string OR a list (composite). VCS and Issues are single-value in v1.
- `pr_body_template` is relative to repo `path`.
- No top-level `providers:` section. Connection details (URLs, project keys, tokens) live in the exec provider's own config under `$XDG_CONFIG_HOME/<provider-name>/` (ZR home-manager module generates these).

XDG paths:

- Config: `$XDG_CONFIG_HOME/pg-pr/config.yaml`
- Cache: `$XDG_CACHE_HOME/pg-pr/` (org-members cache, response cache)
- Data: `$XDG_DATA_HOME/pg-pr/` (durable state if any)
- State: `$XDG_STATE_HOME/pg-pr/` (repo-state.json, last-sync timestamps)
- Runtime: `$XDG_RUNTIME_DIR/pg-pr/` (daemon lockfile, IPC if added later)

## Auth

Per-provider delegation. `pg-pr` never stores credentials itself.

| Provider                     | Source                                                      |
| ---------------------------- | ----------------------------------------------------------- |
| `github` (VCS, CICD, Issues) | `gh auth token` invoked at startup.                         |
| `jira` (Issues, builtin)     | `JIRA_API_TOKEN` + `JIRA_EMAIL` + `JIRA_BASE_URL` env vars. |
| Exec providers               | Their own concern; pg-pr passes through env.                |

`pg-pr auth status` iterates configured providers and reports:

- `OK` (token valid, scopes sufficient)
- `MISSING` (no credentials present)
- `EXPIRED` (call failed with 401)
- `INSUFFICIENT_SCOPES` (specific missing scope listed)

Non-zero exit per failing provider; output is a table by default, JSON with `--json`.

## gascity pack contents (build output)

The pack is a build artifact emitted by `modules/pg-pr-zr/default.nix`. Output store path contains:

- `orders/pr-watcher.toml` — every 10m, runs `pg-pr sync` then `pg-pr changes --since <last-tick>` and dispatches `pr-triage` if new feedback.
- `orders/wake-on-work.toml` — preserves the existing reconciler-bug workaround.
- `agents/pr-self-fixer/prompt.md` — claims `process-feedback` beads on own PRs. Reads feedback, creates action beads, closes feedback with reasons, may do fixes in worktree (action kind=fix-ci uses `pg-pr ci rerun-failed`; action kind=apply-suggestion does the code edit + push).
- `agents/pr-reviewer/prompt.md` — claims `process-feedback` beads on team PRs (where author != self). Creates draft review via `pg-pr review draft`; doesn't post (deferred to human OR a separate gascity escalation).
- `agents/pr-triage/prompt.md` — claims `process-feedback` beads, clusters feedback, dispatches.
- `scripts/...` — helpers invoked by orders/agents; all call `pg-pr` and `bd`. No raw `gh` calls remain.
- `formulas/` — empty directory required by gascity runtime.

The source `pack-src/` may be organized however convenient; the derivation transforms it into the structure above.

- Watch-mode CICD (`gh run watch` parallel) like `/cicd:watch-pr-checks`: may live as a future `pg-pr ci watch <pr>` verb or as an org-specific kubectl-style plugin. Not v1.

- `status=hooked` semantics: bd's `hooked` status nominally means "gated by a hook callback". Used here for feedback beads to keep them out of `bd ready` while the processing-cycle bead drives closure. ## Post-v1 design directions

Two features deferred for design after Phase 4 ships. Captured here so Phase 5 / 6 work has a starting point.

### Unified PR description generation

PR descriptions are generated by an LLM regardless of who initiates the create/update — direct claude session, agent in a gascity session, or human running `pg-pr pr create` at the terminal. The same prompt/logic drives all three paths.

Mechanism:

- The pg-pr-plugin ships a SKILL (not a slash command), because agents may auto-decide to create PRs and a SKILL auto-triggers on relevance. Path: `packages/pg-pr-plugin/share/pg-pr-plugin/skills/pg-pr-write-pr-description/SKILL.md`.
- The skill body instructs the agent: gather context by calling `pg-pr pr show <n> --json`, `pg-pr pr files --json`, `pg-pr pr commits --json` (plus diff if needed); synthesize a description; emit via `pg-pr pr update <n> --body-stdin` (or `pg-pr pr create --body-stdin`).
- For direct CLI invocation (`pg-pr pr create --generate-description`), the CLI invokes `zr-agent <skill>` (the existing generic agent-CLI wrapper) which spawns a fresh agent that reads the same SKILL. That subprocess agent then calls back into `pg-pr` in a new process. Two-process trip is acceptable; consistency wins over process count.
- Context aggregation lives in the CLI (verbs already exist: `pr show`, `pr files`, `pr commits`). The skill is thin; it composes existing verbs.

Why a SKILL rather than a slash command: a command is invoked deliberately; a skill auto-triggers on intent. Agents creating PRs autonomously must follow the same prompt as humans typing the command, so the trigger-by-intent path is the safer surface.

### OTEL + Prometheus instrumentation

Tracing:

- Span boundary = one sync run per repo. Nested spans are fine for provider calls and bd writes, but the unit of work is the repo-level sync.
- Allowed trace attributes (no PII risk): `repo_name`, `pr_number`, `run_id`, `author_email`.
- Comment body, review body, file paths in a private repo: not added to traces yet. Comment body is probably acceptable but deferred until a privacy review.

Endpoints:

- OTEL OTLP endpoint resolved via env var (per `~/gc`'s pattern — confirm exact var names). Missing/unreachable endpoint emits a one-line warning on stderr at startup, does NOT fail.
- Daemon mode exposes a Prometheus scrape endpoint on `127.0.0.1:<port>` (default port TBD; configurable). Metrics: per-PR sync duration histogram, sync errors counter (labeled by repo), feedback beads created counter, ci-only-attempts gauge, last-successful-sync-time gauge.
- Standalone `pg-pr sync` (one-shot) emits traces but no metrics endpoint.
