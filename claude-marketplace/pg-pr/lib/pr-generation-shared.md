# pg-pr PR generation — shared reference

Shared by the `pg-pr-write-pr-description` and `pg-pr-write-pr-title` skills.
Both are invoked the same way — a direct claude session, an agent inside
another session, or pg-pr's own shell-out (`pg-pr pr create
--generate-description` / `--generate-title`) — and both need the same
repo/PR context and the same content rules before they diverge on what
they actually emit (a multi-section body vs. a one-line title). Read this
before following either skill's own SKILL.md.

## Establish PR context

Pick **one** of these modes:

- **Creating a new PR**: the user has not yet opened the PR. You need the
  repo, the head branch, and (for description generation, when updating)
  a title.
- **Updating an existing PR**: the PR already exists. You need the PR
  number and the repo. (`pg-pr-write-pr-title` is only ever invoked at
  creation time — `pg-pr pr update` has no title parameter at all — so
  this mode does not apply to it.)

If repo/branch aren't supplied, detect them:

```bash
pg-pr branch detect --json
```

That emits `{"repo": "...", "branch": "..."}` for the current working
directory.

## Gather context

Always run, in this order:

```bash
# 1. Existing PR body (only if updating a description).
pg-pr pr view <pr> --repo <owner/name> --json

# 2. Changed files with add/delete counts.
pg-pr pr files --base origin/main --json

# 3. Commit subject + body lines on this branch.
pg-pr pr commits --base origin/main --json
```

- `pr view --json`'s `identity.body` is the PR's existing description.
  When updating a description, treat it as the starting point — preserve
  any hand-authored sections that look intentional (e.g. a "Notes for
  reviewer" block). Title generation only ever runs at PR creation, so
  this step doesn't apply there.
- `pr files --json` returns `{"files": [{path, additions, deletions,
binary}, ...]}`. Use it to see the shape and area of the change.
- `pr commits --json` returns `{"commits": [{sha, subject, body,
author}, ...]}`. Commit subjects are the primary input for both a
  description's Changes section and a title.

If `--base origin/main` is wrong for this repo (e.g. the default branch
is `develop`), pass a different `--base`.

## Content rules

**Include:**

- The "why" (problem, goal, user-visible effect).
- Major behavioural changes, with the file or area name.

**Exclude:**

- Secrets, tokens, internal URLs, host-private paths
  (`/Users/<name>/...`, `/home/<name>/...`).
- File paths outside the repo.
- Commit body trailers that look auto-generated by Claude / Gemini /
  Copilot (e.g. `Co-authored-by: Claude`, `Generated-by: ...` blocks).
  Summarise the human-meaningful changes instead.
- "Thinking out loud" commentary the human wouldn't want in the final
  output.
- Any employer/organization identifier that isn't already visible in the
  repository's own public history — this content can end up in a public
  repo's PR title or body.

**Tone:** matter-of-fact, present tense, technical. Match the
repository's other recent PRs if you can see them via `gh pr list` or
`pg-pr pr view` on adjacent PRs.

## What NOT to do (either skill)

- Don't call `pg-pr pr merge` or `pg-pr pr automerge`. Those are
  human-only verbs.
- Don't post comments or reviews from either of these skills.
