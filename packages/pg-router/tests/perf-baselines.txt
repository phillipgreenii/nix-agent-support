# Method: internal/eventqueue/bench_test.go's
# BenchmarkDispatchQmuHoldTimeP99AtTenK and BenchmarkExpireQmuHoldTimeP99AtTenK,
# run manually via:

#   go test ./internal/eventqueue/... -run '^$' -bench 'QmuHoldTimeP99AtTenK' \
#     -benchmem -benchtime 2000x
#
# Each benchmark drives its call with a 10,000-entry queue and reports a
# custom `p99-ns/op` metric (computed by hand across per-call samples, since
# the standard `ns/op` a Go benchmark reports on its own is a MEAN, not a
# tail figure, and ADR 0031's concern here is the tail). Dispatch's own
# benchmark keeps a persistent queue and one always-accepting listener, so
# phase 2 (unlocked Offer) does negligible work and each call's wall time is
# dominated by phases 1 ("SNAPSHOT", locked) and 3 ("RECORD", locked)
# together; there is no public seam to split those two further without
# instrumenting q.mu itself (out of this packet's Files). Expire's benchmark
# is a single q.mu critical section end to end, so its wall time already IS
# the lock hold time, not merely a proxy for it — but note its own `ns/op`
# column also includes the per-iteration 10k-entry setup this benchmark must
# redo every call (Expire consumes/depletes what it retires), so only the
# `p99-ns/op` figure below is the one that isolates the call itself.
#
